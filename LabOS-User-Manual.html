PROGRAMME WORKSPACE

Track one programme without hunting across modules

Open a programme from Validation, Planning or any programme link. The dedicated workspace is the single operational home for that programme.

What is consolidated

  • Programme/customer/product identity, due date, delivery risk and next action.
  • Visual validation Test Leg / sub-leg flow.
  • Week, Month, Quarter and Year programme swimlane planning.
  • Serialized samples and the tests to which each DUT is assigned.
  • Requirements/specifications, prototype dependencies and method-development readiness.
  • Budget, actuals and forecast-at-completion.
  • Execution, quality issues and test reports.

Sample allocation

Every test and nested sub-test leg has ◇ Samples. Choose Automatic to inherit/split the predecessor population, or Specific to select exact serial numbers. LabOS only offers predecessor-compatible samples so genealogy remains valid.

Changing samples after planning

The unlocked booking is invalidated and the affected programme is replanned because DUT count can change duration/batching and resource demand.

WORKFLOW 1

Request and coordinate a prototype build

Use this when validation samples depend on a prototype build rather than direct sample supply.

1Define the build

Enter build name, quantity, material-available date and expected build-completion date.

2Link precisely

Link to the entire programme, a main Test Leg, or one specific test. This determines which sample-readiness gate the build controls.

3Schedule finite resources

LabOS coordinates the build with prototype equipment/staff and downstream validation demand.

4Update real progress

Material arrived, build started, progress, new forecast, completion and release evidence are separate states.

5Handle a delay

Update expected completion and reason. Default recovery protects other programmes; optionally compare priority trade-offs.

6Release samples

Completion evidence plus sample release makes the linked validation gate executable and triggers a protected replan.

If the build slips

Do not manually edit downstream test dates. Update the prototype forecast. LabOS propagates the new readiness date, calculates the linked validation impact, then presents a recovery decision. Other programmes remain protected unless the user explicitly allows them to move.

Step 1 · Programme & samples
  • Define customer/project/product/revision, priority and required completion.
  • Choose sample source: direct availability date, existing prototype build, or create a new linked prototype build.
  • Enter DUT population. LabOS pre-populates serials such as AUTO-SN-001; overwrite any serial with the actual identity.
  • Do not mark future expected samples as physically released. They can drive planning, but execution still requires custody/release evidence.
Step 2 · Visual test flow

Each main Test Leg is independent. Inside a leg, use Next for sequence, Split for parallel DUT paths, and Merge only when branch evidence is complete. Any sub-branch can split again (for example 1a → 1aa / 1ab). Desktop supports drag-and-drop; mobile uses Move. Use ◇ Samples on every test/sub-leg to assign exact serials, or retain automatic population inheritance.

Method choice at every test: select a standard Test Library method or define required specifications. LabOS assesses whether an existing method fits, needs adaptation, or requires new test development and lead time.
Step 3 · Readiness review

LabOS checks sample source/serial population, method maturity, specifications/acceptance criteria, predecessors, equipment/calibration and qualified staff. Failed checks must show a Resolve → action.

Step 4 · Schedule

Request planning only after readiness inputs are structurally complete. Expected future samples may be scheduled after their expected availability. If the solver cannot schedule all tests, LabOS must route you into blocker recovery rather than silently producing a partial plan.

WORKFLOW 3

Schedule, resolve blockers, then decide

The Schedule action follows a fixed decision loop. If eight tests are unscheduled, LabOS must not claim “nothing needs to move” or allow a meaningless Apply action.

When scheduling cannot complete

  • Routine equipment/staff contention and predecessor sequencing are solved by the planner first; they are not user blockers. Hard blockers are grouped by family: samples/custody, method readiness, calibration/asset readiness, competency, specification/release and other physical/governance gates.
  • Only genuine hard blockers have Resolve →. Planner-owned contention has Auto-resolve →.
  • Resolve the actual condition and provide evidence.
  • Select Retry scheduling, or use Auto-plan from the dedicated Programme Workspace.
  • Only a feasible proposal can be accepted/applied.

When there is a trade-off

  • Default: protected replan of the affected programme.
  • Optional: allow selected programmes X/Y/etc. to yield resources.
  • Review programme-by-programme due-date and booking impact.
  • Accept or reject the alternative.
  • Accepted scheduling changes retain Undo/restore capability.

WORKFLOW 4

Execute only when the real readiness gates are satisfied

Ready test

  1. Open the execution work item.
  2. Confirm allocated serial-numbered DUTs and custody.
  3. Confirm equipment and calibration validity.
  4. Confirm qualified operator.
  5. Run guided LES/checkpoints.
  6. Capture logged data, result evidence, deviations and actual time.

Blocked test

Blocked items show Resolve blocker →, not only a disabled Start button. The same guided-blocker workflow is used whether the user reaches the issue from Planning or Execution.

Important

Expected sample date, approved proposal, planned calibration or planned prototype completion do not equal objective completion evidence.

Verify

A lesson is not the end product. LabOS should show what it does with the lesson:

  • Correlate repeated issues with the same method/equipment/condition.
  • Form a proposal with hypothesis, confidence, expected benefit and closure contract.
  • User accepts or rejects the proposal.
  • Acceptance creates an implementation workflow; it does not claim the change happened.
  • Real implementation evidence is captured.
  • Subsequent runs verify effectiveness. Recurrence can reopen the issue or reduce confidence.

If a modal has no viable action

That is a workflow defect, not something the user should work around. Close it and use the nearest Guided workflow / Resolve blocker → entry point. In v1.17 schedule and execution surfaces are designed to route to the blocker itself.

Traceability principle

Every validation decision should remain traceable to customer/programme/product, requirement/specification, Test Leg/test, DUT serial/genealogy, prototype dependency, equipment/asset/calibration, operator/competency, logged data, quality events, report and approval. Planned state and evidence state are intentionally separate.
